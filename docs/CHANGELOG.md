- Backend quality gates: `ruff`, `black`, `mypy`, `pytest` — all passing.
- Frontend quality gates: `eslint`, `prettier`, `tsc`, `vitest`, `vite build` — all passing.
- `docker-compose.yml` (local Postgres + backend) and backend `Dockerfile`.
- GitHub Actions CI (`.github/workflows/ci.yml`): backend lint/format/type-check/migration-check/tests against a Postgres service container; frontend lint/format/type-check/tests/build.
- Full initial database schema (`backend/migrations/versions/0001_initial_schema.py`) covering every table in `DATABASE.md`, including the booking/event GiST exclusion constraints and the append-only `audit_logs` grant revocation.
- **Module 1 — Authentication**: backend `/api/v1/auth/{register,login,logout,password-reset,me}` (`API.md` §2) delegating to Supabase Auth via the service-role key; `get_current_user`/`require_role` FastAPI dependencies enforcing RBAC server-side. Frontend `AuthProvider`/`useAuth`, Axios client with bearer-token interceptor and 401 handling, `RequireAuth`/`RequireRole` route guards, and Login/Register/Forgot-password pages styled per `UI_UX.md`. Backend integration tests (register/login/me/logout/password-reset happy-path + failure cases) and frontend form-validation tests.
- **Module 2 — Dashboard**: `AppShell` persistent sidebar with the exact per-role information architecture from `UI_UX.md` §4, role-specific `DashboardPage` with quick actions (FR-10.3) and an "needs attention" panel (FR-10.2, honest empty state — wired to real data as each owning module lands). Every nav destination routes somewhere real now (a labeled placeholder until its module is built), so no dead links. Role-gated-rendering tests for both the shell and the dashboard.
- **Module 3 — Classroom Booking**: `buildings`/`rooms` admin-managed master-data endpoints (`API.md` §4); `bookings` service implementing the full conflict-validation order from `RULES.md` §3.3 (room active → maintenance block → confirmed-booking overlap → role), a room-row `SELECT ... FOR UPDATE` lock plus the DB exclusion constraint as a second line of defense, and the exact `RESOURCE_CONFLICT` 409 error shape from `API.md` §5 including the conflicting window. Frontend: room search + availability + booking creation flow, "My Bookings" list with cancel, all styled per the plaque-card/status-badge system in `UI_UX.md`. Backend test coverage includes dedicated boundary-case tests for overlap detection (exact overlap, partial overlap, touching-is-not-a-conflict, cancellation freeing a slot, maintenance-block exclusion) plus full RBAC/lifecycle integration tests; frontend has a role-gated + empty-state test for the bookings list.
- **Module 4 — Lab Reservation**: `/labs/availability`, `/labs/reservations`, `/labs/waitlist`, `/labs/waitlist/{room_id}` (`API.md` §6), reusing Module 3's conflict-checking core (`app/services/booking/service.py::create_booking_or_raise`, refactored out of the classroom router so both share one validated path) with a `RoomType.LAB` constraint. Waitlist join requires an actual conflict on the requested window (400 `SLOT_AVAILABLE` otherwise) and assigns a queue position. `GET /bookings`/`GET /bookings/{id}`/`PATCH /bookings/{id}/cancel` were broadened from faculty-only to owner-scoped-for-any-role, since students now legitimately own lab bookings (`DECISIONS.md` ADR-013). Frontend: "Reserve Lab" page (student + faculty) with reserve/waitlist actions reusing the availability-search pattern from Module 3. `UI_UX.md` §4's Student IA gained "Reserve Lab" (was already present for Faculty; the student entry was a doc gap, now fixed).

- **Module 5 — Hostel Complaint Management**: `POST /complaints` (multipart, Supabase Storage upload via a new `app/core/storage.py` type/size-validated helper), the full state machine from `models/complaint.py::VALID_COMPLAINT_TRANSITIONS` enforced on every transition endpoint (`assign`, `status`, `verify`), ownership checks (reporter/assignee/warden/admin) on read and write. A minimal `GET /users` (`app/services/users/router.py`) was pulled forward from Module 14 so the warden's Complaint Queue can pick a `maintenance_staff` assignee — scoped so a warden can only ever see maintenance staff, never other users (`DECISIONS.md` ADR-015). `complaints` gained a `completion_image_url` column distinct from the original report `image_url` (`DECISIONS.md` ADR-014), so evidence of the problem isn't overwritten by evidence of the fix. Frontend: Submit Complaint form (multipart), My Complaints (with Verify action), Complaint Queue (with inline Assign). Backend tests cover every valid/invalid state transition plus RBAC/ownership at each step; frontend has an empty-state + conditional-action test.

- **Module 6 — Maintenance Tracking**: `GET /maintenance-requests`, `PATCH /maintenance-requests/{id}` (`API.md` §11). `maintenance_requests` gained a `status` column (`pending`/`in_progress`/`completed`) it was missing despite `API.md` already promising a status update (`DECISIONS.md` ADR-016). Assigning a complaint (Module 5) now also creates the linked `maintenance_requests` row — the only path that populates this table today, giving technicians a real "My Tasks" list end-to-end without needing Module 7 first. `actual_completion` auto-stamps when a technician marks a task `completed`; a completion photo uploads to the same `maintenance-completion-photos` bucket Module 5 uses. Frontend: single "My Tasks" view serving all three of the maintenance_staff nav items (My Tasks / Update Status / Completion Upload), with inline status-advance + photo actions. Backend tests cover technician-scoped visibility, ownership on update, and the auto-`actual_completion` behavior; frontend has an empty-state + next-action test.

- **Module 7 — Equipment Inventory**: `GET/POST /equipment`, `PATCH /equipment/{id}` (admin master data) plus a new `equipment_requests` flow backing FR-7.3 — `POST /equipment/{id}/request` (faculty), `GET /equipment/requests` (admin), `PATCH /equipment/requests/{id}/{approve,reject}` (admin; approving flips the equipment's own `status` to `in_use`). This is a new table (`DATABASE.md` §2.17) since neither `API.md` nor `DATABASE.md` had any path for FR-7.3 before (`DECISIONS.md` ADR-017). Frontend: faculty-facing Equipment Requests page (browse available equipment, request, inline confirmation).

- **Module 8 — Lost & Found**: `POST /lost-found` (student, image optional — unlike Module 5's complaint photo, which is required), `GET /lost-found` (any authenticated, filterable by type/status/keyword via `ILIKE`), `PATCH /lost-found/{id}/status` (reporter or admin only, matched/closed). Frontend: single page combining search (open to all roles) with a report form (student-only, shown conditionally).

- **Module 9 — QR Attendance**: `POST /attendance/sessions` (faculty; `secrets.token_urlsafe(32)` token, 5-minute default/30-minute max expiry — `DECISIONS.md` ADR-018), `POST /attendance/scan` (student; server-side expiry + duplicate-scan checks, `409 DUPLICATE_SCAN`/`400 TOKEN_EXPIRED`), `GET /attendance/sessions/{id}/records` (owning faculty or admin), `GET /attendance/reports` (own sessions for faculty, all for admin, with a scan-count aggregate). Frontend: QR generation page (`qrcode.react`, new dependency) with a live-polling scanned-students list, a reports page, and a manual-entry scan page for students.

- **Module 10 — Event Scheduling**: `GET/POST /events`, `PATCH /events/{id}/cancel` (`API.md` §8) — faculty/admin create events against the `events` table's own GiST exclusion constraint (`DATABASE.md` §2.9), validated against `maintenance_schedules` and other scheduled events (never against `bookings`, since auditorium/seminar_hall room types never appear there — classroom booking and lab reservation both force a different `expected_type`). Frontend: venue-picker + datetime form reusing the same conflict-surfacing pattern as Module 3's booking flow.

- **Module 11 — Notification Center**: `GET /notifications` (own, `?unread=`), `PATCH /notifications/{id}/read` (own), `GET/PATCH /admin/notification-settings` (admin) — `API.md` §12. Frontend: `core/supabase.ts` (new browser Supabase client, anon key only, per `DECISIONS.md` ADR-010), a bell in `AppShell`'s top bar and a full `NotificationsPage`, both backed by TanStack Query polling (15s) as the always-working baseline plus a best-effort Supabase Realtime subscription that invalidates the cache instantly on insert — polling still covers the case where Realtime isn't reachable. Admin `NotificationSettingsPage` for FR-11.6.

- **Module 12 — Reports & Analytics**: `GET /analytics/{room-utilization,complaints,attendance,equipment,maintenance}` (`API.md` §13, FR-12.x), role-scoped per FR-12.4 (admin: everything; warden: complaints only; faculty: attendance only). `/analytics/attendance` reuses the exact query behind Module 9's `/attendance/reports` (factored into `app/services/attendance/service.py::get_session_reports`) rather than a second implementation — `DECISIONS.md` ADR-019. `maintenance_requests` gained a `created_at` column (same ADR) since "maintenance performance" needs a creation timestamp to measure resolution time against, which didn't exist before. Frontend: `AdminReportsPage` with Chart.js bar charts (room utilization, complaints by status, equipment by status) and stat tiles for maintenance metrics, all on the token palette per `UI_UX.md` §10.

- **Module 13 — Audit Logs**: `GET /audit-logs` (`API.md` §14, FR-13.2), filterable by `actor_id`/`entity_type`/date range, paginated. ### Fixed
- First run against a real Postgres/Supabase project (rather than the `FakeSupabaseClient` test double) surfaced two bugs invisible to the test suite: every enum-typed column was writing the Python member's `.name` instead of its `.value` (`DECISIONS.md` ADR-020), and JWT verification assumed every Supabase project signs with a shared HS256 secret, which isn't true for projects using Supabase's newer asymmetric signing keys (`DECISIONS.md` ADR-021). Both are fixed; registration and login now work end-to-end against a live Supabase project.
- Alembic's `env.py` passed `DATABASE_URL` through `configparser`-backed `set_main_option` unescaped; a password containing a literal `%` (common in generated Supabase passwords) broke config interpolation. Fixed by escaping `%` to `%%` before it reaches the ini parser.

### Deferred (tracked, not forgotten)
- The Reports & Analytics page doesn't have a date-range filter control yet, even though `GET /analytics/room-utilization` and `/analytics/maintenance` already accept `from`/`to` query params server-side — UI wiring for it is the remaining piece (`PRD.md` FR-12.2).
- Data export (CSV/PDF) is explicitly a stretch goal in `PRD.md` FR-12.3/FR-7.3 and isn't implemented.
- Event reminders (the seeded `event_reminder` notification type) need a scheduled/delayed trigger, which requires a task-queue/cron mechanism not yet part of this stack — immediate (non-scheduled) notification types are all wired, but "remind me before it starts" is not.
- Actual email dispatch (when `notification_settings.email_enabled` is true) isn't implemented — no email provider is configured, and `PRD.md` §8 marks email optional/supplementary for v1. The setting is fully manageable by admin; it just has no effect yet.
- Real camera-based QR scanning isn't implemented — `ScanAttendancePage` takes the token via manual text entry, since a camera-scanning library can't be meaningfully verified without a physical device in this environment. The API contract (`POST /attendance/scan`) is unchanged either way.
- FR-3.4 (notify a waitlisted user when their slot opens) needs the Notification Center (Module 11) to exist before it can fire. The trigger point is marked with a code comment in `PATCH /bookings/{id}/cancel` (`app/services/booking/router.py`) — see `DECISIONS.md` ADR-013.
- Real-time complaint status updates (FR-4.4) currently rely on TanStack Query refetching, not a live Supabase Realtime subscription — that wiring is Module 11's job too.
- Standalone (non-complaint) maintenance requests have no creation path yet — revisit once Module 7 (Equipment Inventory) needs to trigger repairs from an equipment status change (`DECISIONS.md` ADR-016).
- A faculty member has no endpoint to view their own equipment-request history (only admin can list `/equipment/requests`) — the frontend confirms submission inline instead of showing a persistent list. Revisit if this becomes a real usability complaint.

### Decisions
- See `DECISIONS.md` ADR-010 (backend proxies Supabase Auth; self-registration always creates a `student` account) and ADR-011 (accepted, reviewed `react-router` advisory — not applicable to this app's routing usage).

### Known Limitations
- Backend integration tests under `backend/tests/integration/` require a reachable Postgres (`DATABASE_URL`) and skip gracefully without one — they run in CI against a Postgres service container, and locally via `docker compose up -d postgres`.
